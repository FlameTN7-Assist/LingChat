# 对话压缩（MemoryBank 记忆自动压缩）失效 — 诊断与修复

> 适用对象：LingChat 维护者 / 贡献者
> 分支：`fix/context-compression-tools`（基座 `upstream/dev`）
> 范围：step 1 修复（恢复压缩功能 + 不破坏工具闭环）；step 2 优化另起讨论。

---

## 一、背景

- **"对话压缩"** 指 `USE_PERSISTENT_MEMORY`（默认开启，设置项描述"开启后记忆会自动压缩，减少 token 消耗"）背后的 MemoryBank 链路：
  - `persistent_memory_system.rs` 把对话压缩成 4 段记忆（短期回顾 / 长期经历 / 用户画像 / 约定）；
  - `role_manager::sync_memories` 用 `get_slice_start_index()` 按行号裁剪上下文窗口，防止上下文无限膨胀。
- **工具调用**引入后（`ai_service/tools/`，`tool_loop` 闭环），工具消息以两条形态回填进 `line_list`：
  - `Assistant` 行携带 `tool_call`（JSON 数组）；
  - `Tool` 行携带 `{"tool_call_id":..., "result":...}`。
  - 二者均 `sender_role_id=None`、`perceived_role_ids = 全场在场角色`。

## 二、根因（按影响排序）

### 根因 1：上下文裁剪窗口可能切断工具调用配对 → 对话直接报错
- `sync_memories` 阶段 3 用 `get_slice_start_index()` 计算 `slice_start = 指针 - recent_window(30)`，然后直接 `source_lines[slice_start..]` 切片，**无工具配对对齐**。
- 一旦某次压缩成功推进指针，`slice_start > 0` 进入"裁剪模式"。若第 `slice_start` 行恰好是 `Tool` 结果行，其配对的 `assistant(tool_call)` 在窗口之外。
- `MemoryBuilder` 对这种情况无防护，会产出**孤儿 `tool` 角色消息**；主流 provider（OpenAI 兼容）会以 400 拒绝"无配对的 tool 消息"→ 对话 / 工具循环报错。
- 反向同理：窗口结尾停在 `assistant(tool_call)` 后而结果未写入 → **悬空 tool_calls**，同样非法。

### 根因 2：工具行被计入"可见台词" → 压缩阈值失真 + 记忆被工具 JSON 污染
- `persistent_memory_system::build_chat_text_and_count` 判定 `visible = sender==role || perceived.contains(role)`；工具行 `perceived` 为全场角色 → 每条工具调用 / 结果都计入 `visible_count`。
- 后果：① 阈值（默认 250）被工具流量"冲高"，压缩比设计更频繁触发；② 压缩 prompt 混入 `tool: {"tool_call_id":...}` 原始 JSON → 记忆质量下降、token 浪费，也加剧根因 3 的失败。

### 根因 3（潜在）：压缩失败 → 指针不推进 → 上下文永不裁剪
- 4 段压缩任一失败 → 指针不动 + 60s 冷却 + 下轮重试。长期失败时记忆永不更新、窗口永不裁剪 → 上下文无限膨胀（越聊越大 / 最终超限）。
- 根因 1/2 会显著抬高失败率（非法上下文 / 污染文本）；修好 1/2 后此问题自然缓解。真正的"失败自愈兜底"列入 step 2 优化。

## 三、修复（step 1，3 个文件，不含前端）

| 文件 | 改动 |
|---|---|
| `role_manager.rs` | 新增 `align_slice_start`：裁剪窗口起点若落在 `Tool` 行，向前回溯到配对的 `assistant(tool_call)`，保证窗口以完整工具轮次开头 |
| `memory_builder.rs` | 维护 `open_tool_call_ids`：孤儿 `tool` 结果（本上下文内无配对调用）丢弃；收尾剥离结果缺失的悬空 `tool_calls`（保留正文）——兜底任何路径产生的非法配对 |
| `persistent_memory_system.rs` | `build_chat_text_and_count` 先过滤工具行（`Tool` 属性 / 带 `tool_call` 的 `Assistant` 行），再统计可见台词与构建压缩文本 |

## 四、测试

- `memory_builder.rs`：完整工具轮次构建顺序 / 孤儿结果丢弃 / 悬空调用剥离 / 多结果轮次配对。
- `persistent_memory_system.rs`：工具行不计入可见台词阈值、不进压缩文本（含 `perceived=目标角色` 的真实形态）。
- `role_manager.rs`：裁剪起点落在 Tool 行回溯 / 普通行不动 / 越界安全。

## 五、验证方式

- Rust 后端不在本地编译（AGENTS.md 约定）：依赖 assist 仓库 `dev-build.yml` 三平台编译 + `cargo test`。
- 前端无改动，无需前端构建。
- 人工验证建议：开启 `USE_PERSISTENT_MEMORY`，自由对话中连续使用网页搜索 / 命令 / 文件工具多轮，观察：
  1. 不再出现"孤儿 tool 消息"类 LLM 400 报错；
  2. MemoryBank 压缩日志正常触发且摘要内容不夹带工具 JSON；
  3. 上下文窗口按预期裁剪（指针推进后最近 30 行窗口）。

## 六、优化方向（step 2，另起讨论，不在本修复内）

1. **工具结果"摘要化"进长期记忆**：目前 `bounded_tool_history` 对写入副本做原文截断（32KB/12KB），可升级为 LLM 摘要，让记忆保留可用的工具结论而非原始输出。
2. **上下文预算管理**：行号裁剪升级为 token 感知 + 完整工具轮次对齐（本修复已做行级对齐，token 级预算可更进一步）。
3. **压缩连续失败自愈**：N 次失败后推进指针 + 明确告警（防"永不压缩→上下文无限膨胀"的静默失效），需权衡"丢记忆"与"保可用"。
4. **非流式 provider 统一工具路径**：MiniMax 已单独降级非流式，可推广为通用 fallback。
